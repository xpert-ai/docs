任务保存要实现的业务结果，一次执行记录保存为实现结果进行的一次尝试。同一个任务可以有多次实施、重试和独立审查，历史记录会保留。

## 派发与后台执行

先创建任务并明确要求，再让负责的 Assistant 派发。执行目标可以是已经配置和授权的外部执行器，也可以是[群项目中明确选入的 Assistant 成员](./group-collaboration)。

派发成功后，会话增加执行卡片，任务增加一次尝试。Assistant 可以结束当前回复，执行继续在后台运行。外部执行器按项目串行接纳，避免同时修改共享工作文件；不同群成员可以并行工作，每位成员同一时间接纳一个正式任务，同一任务的尝试也保持串行。

任务管理本身不提供执行环境。可用 Coding 执行器由部署配置决定；当前 Computer 执行环境由 Pro 提供。

## 任务状态怎么变化

| 状态 | 含义 | 下一步 |
| --- | --- | --- |
| 未开始 | 任务已保存，或要求返工后等待新尝试 | 检查条件并明确派发 |
| 进行中 | 当前实施已实际启动 | 查看执行过程或等待结果 |
| 待验收 | 当前实施运行成功，尚未确认业务结果 | 检查要求、结果和文件 |
| 已完成 | 已作出有效的完成决定 | 交付结果，推进后续任务 |
| 已阻塞 | 失败或其他问题需要处理 | 读取错误和保留结果，决定如何恢复 |
| 已暂停 / 已取消 | 业务任务被明确暂停或取消 | 按业务决定处理 |

执行成功、全部步骤完成或进度 100% 均不能替代验收。取消某一次运行也不会自动取消整个业务任务。

## 结果返回到哪里

结果保存后会送回原负责 Assistant 的会话。允许自动续跑时，Assistant 可以继续检查结果或安排后续工作；打开的会话会显示后续回复。

| 会话情况 | 结果处理 |
| --- | --- |
| Assistant 正在回复 | 保存并排队，等待当前轮次处理 |
| 当前轮次已经结束 | 在原会话继续后续回复 |
| 等待输入或审批、已暂停或被用户停止 | 保存结果，保留等待或停止状态 |
| 服务暂时不可用 | 根据已保存记录恢复结果投递 |
| 会话不可用或授权被撤销 | 保留记录，显示无法继续的原因 |

重新连接会话可以读取已保存的结果和回复。卡片状态与完整回复可能先后更新；看到执行结束但还没有回复时，先查看执行记录的结果投递状态。

## 确认完成

负责的 Assistant 可以检查结果并作出决定；具备项目编辑权限且可访问对应执行和结果的用户也可操作：

1. 打开任务详情的**执行记录**，确认最新实施已成功。
2. 对照当前完成要求检查实际输出，必要时打开或下载[产物](../setup/files-and-deliverables)。
3. 填写检查项和验收理由，选择**确认完成**。
4. 确认任务变为已完成，并保留本次决定对应的执行和结果记录。

验收与当前要求、实施及结果版本绑定。修改要求、产生新实施或替换证据后，旧的通过报告不能直接用于新一轮验收。应用管理的任务应按对应应用流程处理。

## 独立审查

可以让负责的 Assistant 委派一次独立审查，得到“通过”“需要修改”或“无法确定”的结论。审查与实施各自保留记录，审查报告本身不会把任务标为已完成。

当前独立审查需要 Pro 提供的 Computer OpenCode 执行器。它检查固定证据，不重新运行实施测试，也不证明文件真实性；负责的 Assistant 可以另用已授权工具查看实际文件或重跑测试。应结合报告中的限制理解结论。

一旦已委派独立审查，最终确认完成必须依据最新有效且通过的审查，不能跳过或引用旧报告。

## 返工、取消与恢复

- **要求返工**：填写问题和修改理由，任务回到未开始；随后明确安排新尝试，原记录保留。
- **取消本次运行**：在执行记录中取消选中的尝试，不等同于取消整个业务任务。
- **重试结果投递**：结果已保存但未正确送达时，用于再次递送已有结果，不重新运行任务工具。
- **运行失败或结果未知**：先查看该次执行和已经产生的文件，确认是否实际启动，再决定新尝试。不要仅因没有回复就重复派发。

更多排查方法见[故障排查](../help/troubleshooting)。
